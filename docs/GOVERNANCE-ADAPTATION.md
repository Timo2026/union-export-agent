## 1. 前提核实：方法论假设 vs 项目实证

| 方法论前提 | 实证查证 | 判定 |
|-----------|---------|------|
| 可分解性低 | 33 skill 独立目录/tool.py，统一 `run(ctx)` 模板；服务按域分文件 | **高可分解** ❌ 假设不成立 |
| 耦合高 | CAT 编排但 skill 独立；适配器隔离后端；状态机原子 | **中度耦合** ⚠️ |
| 接口不稳定 | skill 契约 `def run(ctx, **kwargs) -> dict`（`_runtime.py:5`）；状态机 13 状态 12 转移（`rfq_state_machine:23-33`）；审计 `log(event,payload,actor)`；配置 6 yaml schema | **已冻结** ❌ 假设不成立 |
| 底层未定 | Timo 引擎 + 四层 RAG + OpenShell4 + Guardrails三段 + egress 闸 + 飞轮 | **已定** ❌ 假设不成立 |
| 验证靠跑通闭环 | 黄金链 6 场景 + 701 pytest + E2E | ✅ 假设成立 |

**一句话**：本项目**不是**"接口未定、底层混乱"的项目；它是"**架构已定、接口已冻结、资产已存在，但没在目标平台（Spark）跑通留证**"的项目。

## 2. 方法论的"采纳"与"修正"

### 采纳（方法论精神对的部分）

| 原则 | 适配动作 |
|------|---------|
| 先停，盘点有什么 | ✅ 已做——MASTER-PRD 八层盘点 + PROJECT-SUMMARY 实测 |
| 定义最小闭环 | ✅ 黄金链就是——收件盘→CAT→报价→验证→回复→审计 |
| 不让所有 Agent 并行拼 | ✅ 采纳——后续不开并行模块开发 |
| 用可运行闭环验证，不投票 | ✅ 黄金链在 Spark 跑通 = 验证手段 |
| 冻结接口再分工 | ⚠️ 核心**已冻结**，只需**补冻几个边界缺口**（见 §3） |
| 模块级跑马替换 | ✅ 采纳——negative trigger / A/B 不达标才重做 |

### 修正（方法论前提不成立的部分）

| 方法论建议 | 为什么不适合本项目 | 修正 |
|-----------|-------------------|------|
| 让 2-3 Agent 做架构跑马选主方案 | 架构**已经选定了**且跑了6个月 | ❌ 不跑马选架构；改为**在 Spark 上验证已定架构** |
